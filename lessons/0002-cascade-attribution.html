Lesson 02 · Cascade attribution

Predict which CSS declaration the resolver keeps

The tangible win: given several matching rules, predict the candidate the Design Tool will display and explain what evidence makes the result trustworthy.

The important correction

Specificity is not the first question. The browser first filters by relevance, origin/importance, and layer. Specificity only compares candidates that survive those earlier stages. See the MDN cascade overview.

1. Start with matching selectors

For a selected element:

<button id="app" class="button">Save</button>

The resolver splits selector lists and asks the browser whether each branch matches:

matchingSelectorBranch(element, selectorText)
  -> element.matches(branch)

This is implemented in resolution.ts. A non-matching rule never becomes a candidate, regardless of how specific it looks.

2. Retrieval practice: specificity

All three rules are normal author rules in the same layer, and all match:

.button       { color: red; }   /* A */
button.button { color: blue; }  /* B */
#app .button  { color: green; } /* C */

Which candidate wins?

The repository calculates this with computeSpecificity(), then stores the winning number in evidence.specificity.

3. Layers beat specificity

@layer theme {
  #app .button { color: blue; }
}

.button { color: red; }

For normal author styles, an unlayered declaration outranks a layered declaration. The high-specificity blue rule does not get to compete on specificity because it loses at the layer stage. This is why frameworks often put generated utilities into known layers.

Which value should the ordinary cascade choose?

The repository models the important/layered/unlayered distinction in compareCascade(). It is an attribution model, not a claim to reimplement every browser cascade feature.

4. Inheritance is not selector matching on the child

.wrapper {
  color: var(--color-text-primary);
}

.wrapper > p {
  /* no color declaration */
}

A selected paragraph can still have a computed color. That value came from the parent because color is inherited by default. The resolver handles this in resolveInheritedProperties():

  1. Resolve directly matching declarations on the selected element.
  2. Walk ancestors for properties in its inherited-property set.
  3. Compare the ancestor's computed value with the selected element's computed value.
  4. Record evidence.inheritedFrom.

Should the paragraph row claim that the paragraph authored the token?

5. Why confidence exists

A candidate can look plausible without being proven. The resolver creates a hidden probe with the authored token declaration and compares its computed result with the selected element's painted value. A match can become exact; inaccessible stylesheets, layers, or ambiguous expressions can lower it to probable or unknown.

Read the final validation pass in getResolvedProperties(), then compare it with the test cases named “higher specificity wins”, “excludes inactive conditional candidates”, and “represents importance, layers and source order” in resolution.test.ts.

Codebase exercise

Open resolvePropertiesFromRules(). For each candidate, identify:

  • where the matching selector branch is recorded;
  • where specificity is recorded;
  • where a later candidate replaces the previous one;
  • where browser-computed output overwrites the provisional resolved value.

If you can answer those four questions without opening the lesson again, you have the core cascade-attribution model.
