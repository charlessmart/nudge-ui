Cascade attribution

How the repository decides which authored declaration is worth showing for a selected element.

Browser concept

  1. Relevance: selector and conditions match.
  2. Origin and importance: author/user/UA and normal/important.
  3. Layer: which cascade layer has precedence.
  4. Specificity: selector weight inside the winning bucket.
  5. Scoping proximity: nearest scope when relevant.
  6. Order of appearance: later wins when the rest ties.

Animations and transitions can sit outside this ordinary authored-rule comparison.

Repository approximation

matching selector branch
        -> element.matches()
        -> importance
        -> layered vs unlayered
        -> specificity
        -> source order

The implementation deliberately reconstructs the parts needed for authored attribution. It then checks the candidate against getComputedStyle() and records exact, probable, or unknown confidence.

Inheritance is a second search

If the selected element has no winning declaration for an inherited property such as color, the resolver walks ancestors. It keeps the ancestor's selector and records inheritedFrom instead of pretending the child authored the value.
