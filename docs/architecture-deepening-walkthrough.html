The one idea

A small doorway, a big room

Good code is organised like a building where each room has one clearly marked door. You should be able to walk up to the “preview verification” room, read the sign, and know what happens inside without opening every cupboard. The technical name for this is a deep module: a small doorway, a lot of behaviour behind it.

The opposite is a room with five unmarked doors and a copy of the same instructions taped inside each one. That is what most of this branch was about. When the same rule is written down four times, the four copies slowly disagree. Nobody notices until a user sees the wrong value, or a test fails for a reason that has nothing to do with the change.

Why this is worth doing at all Every change on this branch is justified by two things: locality (a fix or a bug lives in one place) and leverage (one implementation serves many callers). Tests come along for the ride: once behaviour sits behind one door, you can test it through that door instead of mounting a whole screen.

Change 1 · Host manifest

Four hosts were writing the same letter by hand Core landed

Nudge UI plugs into four different development servers: Vite, Next.js, Astro, and a plain static file server. Each of them has to hand the browser a small note — a “manifest” — that says where things are. Think of it as four receptionists each typing the same welcome letter. The wording drifted: two wrote the version number by hand, one said “reload the page” and one said “refresh the note”, and two said nothing at all about reloading.

Before

After

Each host now adds only what is genuinely its own.

What changed

  • createNudgeUiClientManifest() owns the envelope: version, revision, and the optional capabilities.
  • NUDGE_UI_CLIENT_MANIFEST_VERSION now derives from NUDGE_UI_MANIFEST_VERSION. There is one number, not two that happen to match.
  • Vite and Astro stopped hard-coding version: 1; those were real copies that never imported the constant.
  • A new conformance test checks every host that can build a manifest without a running server: the version parses, capabilities are plain booleans, and a document-reload strategy must announce its events.
What is not done The four hosts still have their own request handlers for the /__nudge_ui__/ routes. Pulling those into one dispatcher is the largest remaining piece (roughly 5–7 days) and touches all four servers at once, so I left it for a follow-up with its own conformance harness. The envelope — where the drift actually was — is fixed.

Look at inspector/clientManifest.ts, hosts/manifestConformance.test.ts, and the four hosts/*/manifest.ts files.

Change 2 · Property fields

Four editors were each re-deciding what a value means Core landed

When you select an element and look at, say, spacing or opacity, the inspector has to answer three questions: is this value backed by a design token, is it an expression like calc(...), and do the selected elements disagree (“Mixed”)? Four different editors answered those questions in their own words. The rules mostly matched — until one of them didn’t.

What changed

  • isExpressionRow() is the single definition of “this row is an expression, not a token”.
  • deriveActiveTokenName() handles mixed selections, calc suppression, and the opacity-specific override in one place.
  • The four editors call those two functions instead of restating the rules.
  • New tests cover the rules directly, without mounting an editor.
What is not done The deeper version of this candidate — one “property field” module that also owns reading, committing, previewing, and reconciling — would replace roughly forty editor components. I did not attempt that. The duplication that was actually causing drift is the value derivation, and that is now shared.

Look at inspector/styleEditors/fieldValue.ts and its test.

Change 3 · Preview trust

The same verification loop lived in two places Core landed

Nudge UI shows you a preview of an edit, then checks whether the browser really applied it. That check needs care: it has to verify the right revision, publish a diagnostic when something didn’t stick, and retry once if a CSS animation was still running. The host page and the Canvas did this with two copies of the same loop. Only one copy handled the animation retry.

Before

After

What changed

  • verifyPreviewChanges() owns the loop, including the “is this attempt still current?” guard before a retry.
  • It accepts its two effects as an argument. A test passes fakes and a fake clock; it never needs a real frame.
  • Both callers now get the animation retry, not just Canvas.
What is not done The stale-change detector remains a separate module. It answers a different question — “does this selector still exist in any live frame?” — and merging it would mix two concepts. I also left the two projection computers alone.

Look at inspector/changes/previewVerification.ts, its test, and the two callers.

Change 4 · Value grammar

“Exactly one var()” was written as five different regexes Core landed

A CSS value like var(--space-4) means “use the token called --space-4”. The inspector often needs to know whether the whole value is exactly one such reference. Five modules answered with their own pattern, and the patterns disagreed: some accepted a fallback, some didn’t; some ignored case; one would happily accept var(--a, red) extra as a single reference because its wildcard swallowed the trailing text.

What changed

  • parseSingleVarReference() scans balanced parentheses instead of using a lazy wildcard. Nested fallbacks such as var(--x, calc(1px + 2px)) parse correctly.
  • The five modules now call it. The alias rule in the token catalog is expressed as “a reference with no fallback”.
  • isCalcExpression() replaces the two local calc checks.
  • A focused test covers the cases the regexes got wrong, including the trailing-text bug.
What is not done The token definitions are still produced by three paths (build-time PostCSS, browser CSSOM, and a serialize/reparse round-trip). Unifying those is a different, larger job. The reported @scope/@container wrapper loss is a bug in the CSSOM path, not a duplication, and should be fixed with a contract test before anyone restructures the producers.

Look at css/value-semantics/cssSyntax.ts and cssSyntax.test.ts.

Change 5 · Session undo

Undo entries held a photograph of a function Core landed

Session undo is one timeline of edits and frame creation. When you undo an edit, the rule is: replay the edit and bring its owning frame back into view. The old code implemented “bring the frame back” by storing a little function inside the history entry, captured at the moment you edited. That works, but it means the history entry can only be understood by running it. You cannot inspect it, serialize it, or test replay without the exact world that existed when it was recorded.

What changed

  • EditHistoryEntry now stores { draftId, cardId? } instead of an activate closure.
  • Replay asks the drafts seam to reveal that frame, then makes the draft active. The domain rule lives in one place, not in a closure per edit.
  • A test asserts that the recorded frame is replayed.
What is not done Canvas history entries still carry undo/redo/dispose closures. Turning those into replayable data means modelling each canvas operation as a command, which is a larger design. The edit half — where cross-draft focus was actually confusing — is done.

Look at inspector/workspace/timeline.ts and inspector/drafts/draftStore.ts.

Change 6 · Canvas ↔ drafts

Two modules were importing each other Landed

The canvas store knew about drafts, and the drafts store knew about canvas. That is a circular dependency: to understand one file you need the other, and a change in either can ripple both ways. Worse, deleting a frame inside the canvas store also fired an HTTP request to delete an HTML file.

Before

After

Drafts still knows canvas; canvas no longer knows drafts.

What changed

  • A small frameLifecycle seam says “can this frame be removed?” and “release this frame’s resources”.
  • The canvas store calls the seam. It no longer imports drafts, the draft key helper, or the artifact client.
  • The workspace controller supplies the real implementation: forget the draft, skip the delete when another frame still uses the artifact, then delete it.
Why this is safe The controller is always running in production, so behaviour is unchanged there. In tests the seam is a no-op by default, which is exactly what a test that only cares about canvas layout wants.

Look at inspector/canvas/frameLifecycle.ts and inspector/workspace/controller.ts.

Change 7 · Agent endpoints

Eight endpoint names existed twice Endpoints landed

The browser and the local agent companion talk over eight small endpoints: /health, /pair, /events, and so on. The companion defined them in one package; the browser typed them out again as fallback strings. They agreed by convention. If someone renamed one, the browser would get a 404 at runtime, not a compile error.

What changed

  • BRIDGE_ENDPOINTS lives in @nudge-ui/agent-protocol, which both sides already depend on.
  • The MCP package re-exports it; the browser transport uses it for all eight fallbacks.
  • The existing bridge tests still pass; a rename would now fail typecheck.
What is not done The UI’s twelve connection labels and tones stay in the UI. They are presentation, not protocol, and moving them into the shared package would couple a label change to both packages. State derivation was already shared through deriveConnectionState.

Look at packages/agent-protocol/src/index.ts and packages/nudge-ui/src/inspector/agent/httpTransport.ts.

Change 8 · Component ids

The same identity string was minted three ways Core landed

Every component the inspector can describe gets an identity string, roughly src/Button.tsx#Button. Three different builders made that string, each with its own idea of which file extension to strip. They happened to agree. If one had stopped agreeing, the inspector would silently fall back to matching by component name.

BuilderBefore
TypeScript contractsfile.replace(/\.(?:d\.)?[cm]?[jt]sx?$/, "") + "#" + name
Package contractsmoduleSpecifier + "#" + exportName
Host policy resolutionstripModuleExtension(source) + "#" + exportName

What changed

  • componentIdentity(moduleSource, exportName) in compiler/sourcePaths.ts owns the format.
  • All three builders call it.
  • Existing compiler and identity tests pass unchanged.
What is not done The single-parse pass and the duplicate import-binding scanners are untouched. That refactor touches the HMR path and the instrumentation code, and a subtle regression there is much harder to see than a duplicated identity string. It needs its own before/after benchmark.

Look at compiler/sourcePaths.ts and the three contract builders.

Change 9 · Dead surface

How to check it

Run these in the worktree

The branch is arch/deepening, based on b09e9d79. Every commit is self-contained, so the easiest review is commit by commit.

pnpm --filter nudge-ui typecheck

pnpm --filter nudge-ui test:unit

pnpm --filter @nudge-ui/mcp test:unit

pnpm lint

The unit suite grew from 2,425 passing tests to 2,443: new tests cover the manifest conformance table, the verification cycle, the value grammar, the field derivation, the frame lifecycle seam, and the replay focus rule. The removals cut 616 lines of dead surface without losing a behavioural test.

Walkthrough generated for branch arch/deepening in .claude/worktrees/arch-deepening. Diagrams are inline SVG and the page has no external dependencies, so it reads offline and prints cleanly.
