# 0042 — Published vanilla-extract contract enrichment

**Labels:** enhancement, needs-triage
**Type:** AFK
**Milestone:** Token inventory and CSS-value fidelity

## User story

As a consumer of a Vanilla Extract design-system package that publishes a
theme-contract export, I see its useful contract paths and provenance alongside
the CSS custom properties the browser applies.

## Current behaviour

The existing Vanilla Extract adapter accepts an already-materialised
`themeContract` object and optional CSS-value map. A consuming app must import
and pass that object through its Vite configuration itself. The experimental
token-compat branch additionally explored a module-path option, but main has
no stable consumer-facing way to load a published contract module.

The CSS catalog is still the authoritative baseline: a package may publish CSS
without exposing an importable contract, and a contract alone does not prove
which value is active in the document.

## Desired behaviour

Add an optional, dev-only configuration seam for loading a published Vanilla
Extract theme-contract module by Vite-resolvable module identifier and named
export. At startup and on module invalidation, the plugin materialises the
contract into adapter records and reconciles them with the active package CSS
catalog by CSS custom-property name.

The resulting token records preserve the actual CSS name and resolved CSS
value, while adding a human-readable contract path and contract/package
provenance where available. Consumers that do not configure this option, whose
package does not publish a suitable contract, or whose contract cannot be
loaded still receive the ordinary CSS-derived catalog without errors.

## Acceptance criteria

- [x] The Vanilla Extract integration accepts an optional Vite-resolvable
      contract module and named export, with diagnostics that explain an
      unresolved module, missing export, or unsupported export shape.
- [x] A nested published contract is materialised into stable human-readable
      paths mapped to its CSS custom-property names.
- [x] Contract entries reconcile with active package-CSS entries rather than
      creating duplicate candidates for the same custom property.
- [x] Browser-resolved CSS values and CSS provenance remain authoritative even
      when contract metadata is present.
- [x] Contract information refreshes safely on dev-server invalidation/HMR.
- [x] No contract configuration is required for normal CSS token discovery;
      a missing or invalid optional configuration fails soft and leaves the
      CSS-derived catalog usable.
- [x] Unit tests cover nested contracts, module/export diagnostics, merging,
      and HMR invalidation. A package-style fixture proves that a contract path
      enriches, but does not replace, an imported stylesheet token.
- [x] The configuration and loaded contract are unavailable in production; the
      dev-only token-catalog contract remains intact.
- [x] `pnpm lint`, `pnpm typecheck`, relevant Vitest and Playwright suites,
      and `pnpm --filter sandbox build` pass.

## Out of scope

- Automatic guessing of arbitrary package exports or executing untrusted
      package code without explicit consumer configuration.
- CSS package discovery (#0041).
- Replacing CSS-derived values with contract-object values.
- A general-purpose CSS-in-JS runtime adapter.
