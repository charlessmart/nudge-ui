# 0040 — Token compatibility module

**Labels:** enhancement, needs-triage
**Type:** AFK
**Milestone:** Token inventory and CSS-value fidelity

## User story

As a designer editing an inspected property, I can choose every token that is
actually compatible with that value slot, even when the tokens come from an
installed design-system package and use an unfamiliar naming convention.

## Current behaviour

The inspector has two separate name-based classifiers: one limits alternatives
in the property editor and another groups rows in the Tokens tab. Their prefix
and property lists recognise only the naming conventions represented by the
sandbox fixtures.

This leaves the picker dependent on naming conventions represented by the
sandbox fixtures. Names such as `--spacing-*` and `--border-radius-*` do not
fit the current picker heuristics, and a valid but unfamiliar token name cannot
be offered safely just because its prefix is not recognised.

## Desired behaviour

Introduce one Token Compatibility module as the sole owner of candidate
selection, compatibility evaluation, grouping, and ranking. Inspector controls
ask this module for candidates; they do not maintain their own token-prefix or
CSS-property lists.

The module's interface should stay small and behaviour-oriented. A caller
provides the selected element, the CSS property being edited, an optional
semantic value slot, the known token entries, and the current token. It returns
compatible alternatives and their presentation groups. A semantic slot handles
editor contexts where the outer CSS property is not the type being replaced,
such as changing the color component of a `box-shadow` value.

Compatibility should be based primarily on the token's concrete, resolved
value in the selected document. For ordinary atomic properties the browser's
CSS grammar is authoritative (for example, validate a candidate using
`CSS.supports("padding", resolvedValue)`). Do not validate `var(--token)`
directly: it is syntactically accepted before its value is known. Adapter
metadata and token names may improve labels and ranking, but must not be the
rule that decides whether a token can be selected.

## Acceptance criteria

- [x] One Token Compatibility module is the shared source of truth for editor
      candidate selection and Tokens-tab presentation grouping; duplicate
      classifier implementations are removed.
- [x] Its interface accepts an element, property, optional semantic slot,
      token entries, and current token, and returns compatible candidates plus
      stable presentation information.
- [x] Candidate eligibility uses resolved CSS values and browser grammar where
      applicable; token names are not the eligibility mechanism.
- [x] Color, spacing, radius, typography, and color-in-composite contexts have
      explicit, independently tested semantics.
- [x] `--space-*`/`--spacing-*`, `--radius-*`/`--border-radius-*`, semantic
      human-readable contract paths, and unrecognised-but-valid names all work
      without adding consumer-specific prefix rules.
- [x] Unit tests cover compatibility and grouping with an injectable browser
      grammar adapter; Playwright covers the picker user flow.
- [x] The dev-only contract remains intact: production builds expose an empty
      token catalog and contain no inspector or identity instrumentation.
- [x] `pnpm lint`, `pnpm typecheck`, relevant Vitest and Playwright suites, and
      `pnpm --filter sandbox build` pass.

## Out of scope

- Editing or rewriting vendor design-system source files.
- Discovering package stylesheets or loading published theme contracts.
- A Newvato consumer-conformance harness.
- Semantic component-prop editing or a general CSS-in-JS adapter.
